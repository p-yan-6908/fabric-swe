Tasks

Every task starts from a real upstream repository pinned to a commit. Bug-fix tasks inject several independent regressions; feature tasks remove a real feature together with its docs; the performance task keeps upstream's own quadratic behaviour. The agent sees an issue-style prompt with symptoms and reproducers, never file or function names.

Method

Arms

ArmIdWhat the agent gets
pi + fabric + foveafabric-foveapi + pi-fabric (full code mode: a single fabric_exec tool) + pi-fovea (code graph)
pi (vanilla)vanillapi with built-in tools only (read, bash, edit, write, grep, find, ls); no extensions

pi 1.4.0; extensions pinned at pi-fabric@0.130.1, pi-fovea@0.33.0. In the fabric arm, fabric_exec is the only tool and fovea is reached from inside it. Fabric's prewalk and subagents are disabled.

How a task is built

  • The upstream snapshot gets a setup patch that injects the bugs or removes the feature, and moves the tests (and snapshots) that would reveal the answer out of the visible suite.
  • Hidden tests combine those upstream tests with extra specification tests whose expected values were recorded against upstream.
  • The workspace is a fresh single-commit git repository with a neutral author and date, so history reveals nothing. Changelogs that would reveal the change are deleted.
  • Injected bugs were chosen by experiment: each candidate was injected alone, the visible failures counted and moved to the hidden suite, and each bug was checked to fail only its own hidden group.
  • Validation proves for every task that each fail-to-pass check fails on the starting state, every pass-to-pass check passes on it, and every check passes with the reference solution.
  • Every hidden assertion is audited against the prompt and the project's docs: it must follow from what the agent is told.

Grading

  1. Test directories are reset to the starting commit and cleaned, so edits to existing tests never count.
  2. The hidden test files are copied in.
  3. Every check runs. A run is resolved when every fail-to-pass and every pass-to-pass check passes.

Isolation and fairness

  • Identical inputs. Every arm gets the same rendered prompt, workspace, model, thinking level, 45-minute limit, retry policy and offline environment (offline flags for pi, uv, pip, Go and npm).
  • Per-run agent directory. Each run gets a fresh pi configuration with only its arm's packages and settings.
  • macOS sandbox. Each agent runs under sandbox-exec. It cannot read the benchmark's tasks, hidden tests, solutions or results, other runs' workspaces, or pi's own sessions.
  • Upstream copies blocked. Known copies of each upstream project elsewhere on disk (Python site-packages, the uv, npm and bun caches, global node_modules, the Go module cache, the Cargo registry) are blocked by per-task patterns.
  • Contamination audit. Every tool call and tool result is scanned for those paths. The count is the "Upstream refs" column; it was 0 for every run.

Metrics

Each run records its status, resolution, every check's pass/fail, wall time, turns, tool calls by tool, tool errors, tokens (input, cache, output, reasoning), API-equivalent cost, peak context, compactions, retries, fabric program count and size, and fovea calls by tool. The per-run numbers behind this page are in data/.

Corrections

After run luna-max-r1 (GPT-6 Luna)

The first full run exposed three task defects. In each one, a hidden check tested behaviour that the prompt does not specify or contradicts. Each defect was fixed in the task, the task was re-validated, and both arms were re-graded with the same corrected checks. Agent code and prompts were not changed, and nothing was rerun.

Limitations

  • One trial per task and arm. Agent runs vary from attempt to attempt; more trials are needed before reading much into differences of one or two tasks.
  • Network is not hard-blocked. Offline flags and the prompt discourage it, but the sandbox allows it.
  • Some copies cannot be blocked. The pinned pi extensions ship an older build of yaml that must stay readable; the transcript audit would flag a reference to it.
  • Memorisation cannot be ruled out for well-known projects. Feature-removal tasks are graded on hundreds of upstream behaviours plus recorded edge cases, which makes reproducing them from memory hard but not impossible.
  • Tasks are not published. Prompts, hidden tests and reference solutions stay private so they do not leak into training data. This page publishes aggregate results only.
